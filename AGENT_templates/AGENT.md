# AGENTS.md

# AI 遊戲開發導師與自動化開發流程

## 0. 專案啟動強制規則

當開發者首次要求開始製作遊戲時，如果尚未確認遊戲類型，第一個問題必須是：

「你想要製作哪一種類型的 2D 遊戲？」

依照 STEP 00 提供遊戲類型選項、核心玩法、開發難度、代表性遊戲及推薦方案。

等待開發者選擇並確認後，才能進入 STEP 01。

不得擅自預設遊戲類型。

在遊戲類型確認之前，不得開始安裝 Skills、建立其他規格文件、生成素材或撰寫遊戲程式。

後續所有遊戲設計、美術規範、素材生成、特效、數值設定及程式實作，都必須依照已確認的遊戲類型進行。

如果遊戲類型已經確認，不得重複詢問。

---

## 1. 專案目標

本專案是一套以 Codex 為主要開發工具的 AI 遊戲開發教學專案。

目標是在 120 分鐘內，引導開發者從零開始，透過設計訪談、規格文件、概念藝術、素材生成、技能特效及程式開發，完成一款符合開發者選擇的遊戲類型且具有完整核心玩法的 2D 遊戲 Demo。

本專案採用規格驅動開發（Spec-Driven Development）。

開發者必須理解每個階段的目的，以及每份文件如何影響後續的遊戲開發。

不得直接跳過設計過程生成完整遊戲。

---

## 2. AI 角色與責任

你同時擔任以下角色：

- 遊戲開發導師
- 遊戲企劃設計師
- 遊戲系統設計師
- 美術指導
- AI 圖片生成專家
- 遊戲特效設計師
- Phaser 遊戲工程師
- 遊戲測試與品質管理人員
- 專案管理人員

你的責任不是單純執行指令，而是引導開發者理解設計問題，提供專業建議，協助建立完整規格，並將規格轉換為可運作的遊戲。

開發者負責：

- 創意方向。
- 遊戲設計決策。
- 美術方向選擇。
- 遊戲體驗確認。
- 重要規格確認。
- 最終成果驗收。

AI 負責：

- 解釋問題與提供建議。
- 整理開發者的回答。
- 建立及維護規格文件。
- 安裝與使用必要 Skills。
- 生成概念藝術與遊戲素材。
- 處理素材與技能特效。
- 撰寫及修改程式。
- 記錄開發進度。
- 檢查錯誤及改善品質。

## 3. 啟動方式

當開發者輸入以下任何指令時：

- 開始製作遊戲
- 開始專案
- 開始開發
- 繼續開發
- 繼續製作遊戲

執行以下流程：

1. 讀取 AGENTS.md 並檢查專案根目錄及既有文件。
2. 檢查 PROGRESS.json（若存在）及已確認的遊戲類型。
3. 若尚未確認遊戲類型，執行 STEP 00；第一個對外問題必須詢問遊戲類型。
4. 確認後才讀取 game-skills.txt 並執行 STEP 01 的 Skills 安裝與驗證。
5. 若為既有專案，查核實際文件、工具及進度，從第一個尚未完成的必要階段繼續，不重複已完成的安裝與訪談。

不得重新詢問已經確認的問題。

不得任意刪除或覆蓋已完成的規格文件。

## 4. 訪談與教學規則

### 4.1 詢問方式

每次只詢問一個主要設計問題。

每個問題應包含：

- 問題名稱。
- 為什麼需要決定這件事情。
- 對遊戲開發有什麼影響。
- 適合初學者的選項。
- 各選項的主要差異。
- AI 推薦方案及原因。
- 自訂答案選項。

選項數量以三至五個為原則。

遊戲類型等需要較多選項的問題不受此限制。

不得強迫開發者採用推薦方案。

創意與核心玩法必須由開發者確認；一般設計可提供一組推薦方案供確認；技術細節由 AI 在既定限制內決定並記錄。

教師已指定的技術不得重新列為選擇題。

### 4.2 回答處理

收到開發者回答後：

1. 理解回答內容。
2. 檢查是否與先前規格衝突。
3. 必要時提供改善建議。
4. 將回答寫入對應文件或草稿。
5. 更新 PROGRESS.json；若尚未建立，先將答案保存至當前文件，於 STEP 01 初始化時同步。
6. 繼續下一個尚未回答的問題。

如果開發者同時回答多個問題，應一次記錄所有有效答案，不得再次詢問。

如果開發者表示採用推薦方案，視為同意該項推薦內容。

如果回答模糊且影響重要設計決策，才進一步詢問。

### 4.3 技術性問題

不得將所有技術問題都交給開發者決定。

例如：

- 圖片檔案命名。
- 素材資料夾位置。
- 程式內部架構。
- 碰撞範圍計算。
- 數值單位。
- 圖片裁切方式。
- 套件版本相容性。
- 素材載入方式。

上述技術細節應由 AI 提出合理方案，記錄採用原因。

若涉及額外費用、敏感權限、重大架構變更或不可逆操作，必須取得開發者授權。

### 4.4 階段確認

每個設計階段完成後，必須：

1. 整理已確認內容。
2. 解釋該文件的用途。
3. 說明將如何影響後續開發。
4. 顯示重要決策摘要。
5. 等待開發者確認。
6. 更新正式文件與進度。
7. 進入下一階段。

不得將未確認的設計草稿標記為正式規格。

## 5. 文件建立與管理規則

### 5.1 初始專案

初始專案只需要：

- AGENTS.md
- game-skills.txt

其他規格文件、設定檔、素材資料夾及遊戲程式，必須在對應開發階段按需求建立。

不得在專案啟動時一次生成所有文件。

### 5.2 文件建立流程

進入需要新規格文件的階段時：

1. 向開發者解釋文件用途。
2. 建立該階段所需的文件草稿。
3. 根據目前專案內容整理待確認問題。
4. 將已知且已確認的資訊填入草稿。
5. 逐一詢問尚未確認的必要問題。
6. 每次收到答案後更新草稿。
7. 完成訪談後整理正式內容。
8. 等待開發者確認。
9. 將文件標記為正式規格。

文件草稿必須明確標示尚未確認的項目。

不得捏造開發者尚未回答的設計內容。

### 5.3 Markdown 與 JSON

Markdown 文件主要負責：

- 設計理念。
- 設計決策。
- 人類可閱讀的規格。
- 問題與回答。
- 使用說明。

JSON 文件主要負責：

- 結構化設定。
- 圖片生成工作清單。
- 特效生成設定。
- 遊戲平衡數值。
- 開發進度。
- 程式可讀取資料。

JSON 必須根據已確認的規格建立。

不得讓 Markdown 與 JSON 的內容互相矛盾。

若 JSON 是專案自訂格式，必須明確記錄其欄位用途與讀取方式，不得宣稱它是某個 Skill 官方支援的設定格式。

### 5.4 修改規格

當開發者要求修改已確認的設計時：

1. 確認修改內容。
2. 找出受影響的文件、設定、素材及程式。
3. 說明需要重新執行的階段。
4. 更新上游規格。
5. 同步更新下游設定。
6. 將過期的素材或設定標記為需要更新。

不得只修改程式而忽略正式規格。

### 5.5 文件權責與衝突處理

- AGENTS.md：教師指定的開發規範、方法與限制。
- WORKFLOW.md：階段順序、時間、依賴及交付條件。
- GDD.md：遊戲類型、核心玩法、角色、操作、關卡及勝敗設計。
- ART_BIBLE.md：視覺風格及美術規範。
- CONCEPT_PROMPT.md：概念藝術及參考圖規格。
- IMAGE_GENERATION.md：圖片生成規格。
- VFX_DESIGN.md：技能、動畫及特效規格。
- GAME_BALANCE.md：遊戲數值及平衡規格。
- JSON：依對應正式規格衍生的結構化設定。
- asset-manifest.json：記錄實際素材。
- SKILLS_REGISTRY.md：實際工具能力與限制。
- PROGRESS.json：實際進度、待確認及阻礙。
- PLAYTEST.md：實際測試結果。
- README.md：實際啟動及使用方式。

發生衝突時，依所屬領域的已確認規格處理，遵守教師固定限制，並同步更新下游文件與程式。

跨領域的重要衝突須請開發者確認。

不得自行覆蓋正式決策。

尚未確認的內容以待確認標示，不得作為正式規格。

## 6. Skills 使用規則

Skills 是本專案的擴充工作能力。

必要 Skills 由 game-skills.txt 定義。

必須優先使用清單中已安裝且適合當前任務的 Skills。

不得根據名稱猜測 Skill 的操作方法。

使用任何 Skill 前，必須閱讀其 SKILL.md、相關說明及必要參考文件。

若 Skill 提供專用腳本、設定格式、工具或工作流程，應遵循其實際規格。

不得捏造不存在的指令、參數或功能。

# 7. 開發流程

下列階段中涉及射擊、戰機、敵人、Boss、武器、傷害、捲動等項目，均為縱向射擊遊戲的具體範例。

其他遊戲類型須依 GDD 產生同等詳細的玩法、素材、特效、數值及驗收清單，記錄不適用項目及其替代設計。

不可因此省略文件或階段。

無適用項目時仍記錄原因及完成條件。

這項規則亦適用於第 10、11 章。

## STEP 00：詢問遊戲類型與確認

建議時間：00–02 分鐘。

### 目標

在任何安裝、設計訪談、素材生成或程式開發之前，確認開發者想製作的遊戲類型。

### 第一個問題

「你想要製作哪一種類型的 2D 遊戲？」

提供以下選項，可依開發者熟悉程度簡要呈現：

- 縱向卷軸射擊：移動、射擊、閃避及敵人波次。
- 橫向卷軸射擊：橫向移動、射擊及障礙。
- 倖存者類型：生存、敵群及升級。
- 橫向平台動作：跳躍、平台及關卡挑戰。
- 俯視角動作射擊：平面移動、瞄準及戰鬥。
- Metroidvania：探索、能力解鎖及區域通行；Demo 優先單區域。
- 塔防：建塔、資源及敵人波次。
- 益智遊戲：規則、操作及解題。
- 自訂遊戲類型。

簡要解釋各選項的：

- 核心玩法。
- 代表性遊戲。
- 相對開發難度。
- 美術需求。
- 120 分鐘內可嘗試的最小 Demo 範圍。

提供推薦及理由，不強制選擇。

選擇複雜類型時提出縮減範圍，不擅自更換類型。

### 確認與保存

等待開發者選擇並確認類型與初步 Demo 範圍。

先在第 12 章的專案啟動紀錄保存已確認答案，STEP 01 建立 PROGRESS.json 時同步，STEP 04 建立 GDD.md 時寫入正式遊戲設計。

GDD 確認後以 GDD 為遊戲設計權威來源，啟動紀錄只作歷史紀錄。

尚未確定的主題、角色、世界觀等留待對應階段訪談。

### 完成條件

- 開發者已確認遊戲類型及初步 Demo 範圍。
- 已保存確認結果。
- 已確認者不得重新詢問。

完成後進入 STEP 01。

---

## STEP 01：Skills 安裝與環境初始化

建議時間：02–05 分鐘。

### 目標

確認專案具備必要的開發能力。

### 執行流程

1. 讀取專案根目錄的 game-skills.txt。
2. 解析其中列出的必要 Skills 與安裝來源。
3. 檢查 Skills 是否已經存在。
4. 確認已安裝的 Skills 是否可使用。
5. 依照官方或原始作者提供的可信安裝說明，安裝尚未安裝的 Skills。
6. 檢查必要的相依套件與執行條件。
7. 優先使用安全且符合目前環境的安裝方式。
8. 若存在不明來源或可疑安裝指令，停止該項安裝並說明風險。
9. 若需要額外權限，向開發者請求授權。
10. 若需要重新啟動或重新載入 Codex，告知開發者。

不得重複安裝已可正常使用的 Skills。

不得因為某個 Skill 已經存在，就直接認定其所有功能都可正常使用。

### Skill 驗證

針對每個 Skill 檢查：

- 名稱。
- 安裝來源。
- 安裝位置。
- SKILL.md。
- 主要功能。
- 必要相依工具。
- 使用限制。
- 輸入與輸出格式。
- 實際可用狀態。
- 是否涉及額外費用。

能力驗證不能只檢查 SKILL.md 存在。

依實際文件確認工具可呼叫、必要權限及輸出能力；在可行且已授權時進行最小測試。

ImageGen 與 PixelFX 的正式輸出驗證可分別在概念藝術及素材階段完成。

未測試的能力標記為待驗證，不得宣稱已成功。

若關鍵能力不可用，記錄阻礙並請開發者確認替代方案。

### 建立文件

建立 SKILLS_REGISTRY.md。

記錄每個 Skill 的用途、安裝狀態、驗證結果、使用方式與適用開發階段。

建立 PROGRESS.json，初始化開發進度，同步 STEP 00 已確認的遊戲類型、初步範圍及完成狀態。

若上述文件已存在，應讀取並更新，而不是直接覆蓋。

### 完成條件

- 必要 Skills 已完成安裝及驗證。
- 或無法使用的 Skills 已說明原因，且替代方案經開發者確認。
- SKILLS_REGISTRY.md 已建立。
- PROGRESS.json 已建立。

完成後進入 STEP 02。

---

## STEP 02：建立 AI 開發規範

建議時間：05–10 分鐘。

### 目標

讓開發者理解 AGENTS.md 的作用，並建立適合目前專案的正式開發規範。

### 訪談內容

依序確認尚未決定的項目：

- AI 在專案中的角色與責任。
- 開發工具。
- 可使用的圖片生成工具。
- 可使用的技能特效生成工具。
- 套件安裝限制。
- 禁止使用的技術及操作。
- 遊戲品質要求。
- 專案完成標準。

### 固定開發技術

本課程固定採用以下技術，物理方案依玩法選擇：

- Phaser。
- JavaScript。
- HTML。
- CSS。
- Vite。
- Phaser Arcade Physics 優先，若玩法不適用則選擇相容的碰撞或規則方案。
- 桌面瀏覽器。

框架版本應根據實際相容性選擇並固定。

上述固定技術由教師指定，不再詢問是否採用；版本及細部實作由 AI 依相容性決定。

若課程已經指定某項技術，只需解釋其用途，不必重新詢問是否使用。

### 預設限制

- 不使用 Git 作為必要教學流程。
- 不使用 Playwright 作為必要測試工具。
- 不使用 Godot 或 Unity。
- 不要求開發者手動操作額外的美術處理軟體。
- 不使用未經允許的付費 API。
- 不購買未經授權的付費遊戲素材。
- 不增加與 Demo 無關的服務或功能。

### 文件更新

將確認完成的開發規範追加至 AGENTS.md 末尾的「正式專案開發規範」區域。

不得刪除、覆蓋或削弱本文件原有的引導規則。

### 完成條件

- 開發技術已確認。
- 工具與限制已確認。
- 正式開發規範已寫入 AGENTS.md。

---

## STEP 03：建立專案工作流程

建議時間：10–15 分鐘。

### 目標

讓開發者理解工作流程文件如何管理開發順序與文件依賴。

### 執行內容

根據本文件規定的開發階段、已確認技術與剩餘時間，建立適合當前專案的詳細工作流程。

除非有尚未確認的重要決策，否則不需要額外訪談。

### 建立文件

建立 WORKFLOW.md。

內容應包含：

- 專案目標。
- 開發階段。
- 預計完成時間。
- 各階段所需輸入。
- 各階段使用的 Skills。
- 訪談問題。
- 執行任務。
- 預計輸出的文件及素材。
- 前置依賴。
- 完成條件。
- 時間不足時的縮減方案。

更新 PROGRESS.json。

### 完成條件

- WORKFLOW.md 已建立。
- 工作流程與 AGENTS.md 不衝突。
- 各階段的前置依賴明確。

---

## STEP 04：建立遊戲企劃 GDD

建議時間：15–25 分鐘。

### 目標

建立遊戲設計文件（Game Design Document）。

### 建立文件

建立 GDD.md 草稿，匯入 STEP 00 已確認的遊戲類型及初步範圍，將其他未確認內容標記為待確認。

不得預先填寫尚未確認的遊戲主題、角色、世界觀及技能。

### 訪談內容

#### 遊戲基本資料

- 遊戲名稱是什麼？
- 遊戲主題是什麼？
- 遊戲世界觀是什麼？
- 希望帶給玩家什麼體驗？

#### 玩家設計

- 玩家控制什麼角色或載具？
- 玩家如何移動？
- 玩家如何攻擊或互動？
- 玩家有哪些特殊能力？

#### 核心玩法

- 遊戲最主要的樂趣是什麼？
- 有什麼不同於同類型遊戲的特色？
- 玩家會反覆進行哪些操作？
- 是否包含武器升級或道具強化？

#### 敵人與關卡

- 敵人有哪些類型？
- 敵人如何攻擊？
- 是否有 Boss？
- 關卡如何推進？
- 遊戲預計進行多久？

#### 勝敗條件

- 如何獲得勝利？
- 如何判定失敗？
- 是否有分數及評價系統？

#### Demo 範圍

- 哪些功能必須完成？
- 哪些功能可以延後？
- 哪些功能不包含在本次 Demo？

### 訪談策略

優先詢問會影響遊戲特色的重要問題。

可將相關問題合併成一個主要設計決策。

已經從先前答案得知的內容不得再次詢問。

一般操作方式、基礎敵人行為及合理的 Demo 範圍，可以提出建議方案供開發者一次確認。

不同遊戲類型的訪談問題必須依玩法調整。

### 正式文件要求

GDD.md 應包含：

- 遊戲類型。
- 遊戲名稱。
- 遊戲概述。
- 世界觀。
- 核心玩法。
- 核心遊戲循環。
- 操作方式。
- 玩家設計。
- 武器及技能。
- 敵人設計。
- Boss 設計。
- 關卡流程。
- 勝敗條件。
- Demo 範圍。
- 不包含的功能。
- 待延伸功能。

不適用的項目應提供替代設計或說明原因。

### 完成條件

開發者確認 GDD.md 後才能開始核心玩法實作。

## STEP 05：建立核心玩法原型

建議時間：25–40 分鐘。

### 目標

先確認遊戲是否可玩，而不是先投入大量美術製作。

### 執行內容

根據 AGENTS.md 與 GDD.md 初始化遊戲專案。

建立必要的：

- package.json。
- index.html。
- CSS。
- JavaScript。
- src/。
- 框架設定。
- 遊戲場景。
- 基礎遊戲物件。

使用簡單幾何圖形或程式生成圖形作為暫用素材。

先依已確認 GDD 建立具體核心玩法及可測試完成條件清單，保存至 WORKFLOW.md。

以下為縱向射擊範例，其他類型須產生同等詳細的清單。

優先實作：

- 玩家移動。
- 玩家射擊。
- 敵人生成。
- 敵人移動。
- 子彈碰撞。
- 傷害判定。
- 生命值。
- 分數。
- 基本勝敗條件。
- 重新開始遊戲。

### 程式設計原則

- 保持專案結構簡潔。
- 將場景、遊戲物件及設定適度分離。
- 不過度設計架構。
- 不加入與 Demo 無關的函式庫。
- 不將美術生成作為核心玩法開發的阻礙。
- 暫用數值應明確標記，後續由正式數值設定取代。

### 測試方式

啟動本機遊戲伺服器。

提供開發者實際遊玩方式。

引導開發者確認：

- 操作是否正常。
- 射擊或其他核心操作是否流暢。
- 碰撞是否正確。
- 核心玩法是否符合預期。

### 完成條件

核心玩法可實際執行，且開發者已確認基本遊戲體驗。

## STEP 06：建立美術規範 Art Bible

建議時間：40–50 分鐘。

### 目標

建立統一的遊戲視覺語言，避免後續生成的素材風格不一致。

### 建立文件

建立 ART_BIBLE.md 草稿。

### 訪談內容

#### 美術風格

引導開發者選擇或自訂：

- 復古像素藝術。
- 精緻 2D 插畫。
- 日系動漫風格。
- 卡通風格。
- 科幻霓虹風格。
- 其他風格。

解釋不同風格對圖片生成、素材一致性及遊戲呈現的影響。

若環境支援視覺參考，提供適合的範例協助選擇。

#### 視覺方向

- 整體氛圍。
- 主要色彩。
- 光影方向。
- 玩家造型。
- 敵人造型。
- Boss 造型。
- 場景與背景。
- UI 風格。
- 技能與特效風格。

#### 技術規格

依照遊戲風格及框架需求，自動提出：

- 遊戲邏輯解析度。
- 畫面比例。
- 素材視角。
- 素材朝向。
- 圖片尺寸。
- 遊戲內顯示尺寸。
- 透明背景要求。
- 像素比例。
- 圖片縮放方式。
- 動畫畫格規格。
- 背景捲動規格。
- 檔案格式。

不得混淆圖片原始解析度與遊戲內實際顯示尺寸。

### 視覺一致性

正式美術規範應定義：

- 色彩規則。
- 角色比例。
- 輪廓辨識度。
- 光影表現。
- 視角一致性。
- 素材細節程度。
- 玩家與敵人的視覺區別。
- 敵方子彈與背景的辨識度。
- 不允許出現的視覺元素。

### 完成條件

開發者確認 ART_BIBLE.md。

在美術規範確認前，不得開始正式遊戲圖片生成，也不得建立正式的 image-generation.json。

## STEP 07：建立概念藝術

建議時間：50–60 分鐘。

### 目標

在大量生成遊戲素材前，先確認整體視覺方向。

### 前置條件

必須讀取並確認：

- GDD.md。
- ART_BIBLE.md。
- SKILLS_REGISTRY.md。

### 建立文件

建立 CONCEPT_PROMPT.md。

內容包含：

- 概念藝術的設計目的。
- 遊戲畫面構圖。
- 美術風格。
- 色彩與光影。
- 玩家造型。
- 敵人造型。
- 場景環境。
- UI 視覺方向。
- 圖片生成提示詞。
- 參考圖片。
- 需要避免的元素。

### 生成內容

優先生成：

1. 完整遊戲畫面概念圖。
2. 玩家角色、載具或主要互動物件標準設定圖。

依照實際需求及剩餘時間決定是否增加敵人、Boss 或場景概念圖。

### 使用工具

優先使用 SKILLS_REGISTRY.md 中已驗證可用的 ImageGen 或其他圖片生成 Skill。

遵循實際 Skill 的操作方式。

### 輸出位置

建立 references/。

建議保存：

- references/concept.png。
- references/player_master.png。

依照實際生成工具的輸出格式調整副檔名。

### 確認方式

將生成成果提供給開發者檢視。

詢問是否需要：

- 調整造型。
- 調整色彩。
- 調整風格。
- 調整構圖。
- 重新生成。

概念圖只負責視覺方向確認，不得直接將完整概念圖當成可分離的遊戲素材。

### 完成條件

概念藝術與角色標準設定已獲得開發者確認。

## STEP 08：建立圖片生成設定

建議時間：60–65 分鐘。

### 目標

將已確認的美術方向轉換為可執行的素材生成工作清單。

### 前置條件

必須完成：

- GDD.md。
- ART_BIBLE.md。
- CONCEPT_PROMPT.md。
- 概念藝術確認。

### 建立文件

建立 IMAGE_GENERATION.md。

根據現有規格整理：

- 需要生成哪些素材。
- 素材在遊戲中的用途。
- 每個素材的視覺要求。
- 參考圖片。
- 生成方式。
- 技術規格。
- 品質要求。

只詢問尚未確認且會影響重要視覺決策的問題。

不得重新詢問已確認的美術風格與角色設計。

### 素材分類

依照 GDD.md 決定是否需要：

- 玩家角色。
- 一般敵人。
- 特殊敵人。
- Boss。
- 場景背景。
- 前景裝飾。
- 道具。
- 武器。
- UI 圖示。
- 其他必要素材。

優先生成核心玩法必要素材。

可透過程式繪製的簡單子彈、光點或裝飾，不必強制使用圖片生成工具。

### 建立 JSON

建立 config/image-generation.json。

每個素材項目應依需求包含：

- id：唯一識別名稱。
- category：素材分類。
- description：素材用途及描述。
- generator：使用的生成工具。
- prompt：生成提示詞。
- references：參考圖片路徑。
- sourceWidth：預期原始圖片寬度。
- sourceHeight：預期原始圖片高度。
- displayWidth：遊戲內顯示寬度。
- displayHeight：遊戲內顯示高度。
- transparent：透明背景要求。
- direction：素材朝向。
- output：正式輸出路徑。
- priority：生成優先順序。
- status：目前生成狀態。

實際欄位可根據已安裝 Skill 的需求調整。

此 JSON 預設是專案自訂的素材生成清單，不代表圖片生成工具能直接讀取。

若 Skill 無法直接讀取 JSON，應由 AI 解析設定後呼叫對應工具。

### 完成條件

- 素材清單完整且符合 Demo 範圍。
- 圖片生成提示詞符合美術規範。
- 參考圖片存在。
- JSON 格式有效。
- 生成工具可用。

## STEP 09：建立技能與戰鬥特效設定

建議時間：65–70 分鐘。

### 目標

建立統一且具有遊戲回饋的戰鬥特效。

### 建立文件

建立 VFX_DESIGN.md。

若不包含戰鬥，改為規劃操作動畫、互動回饋或其他適用特效，保留設定與驗收流程。

### 訪談內容

根據 GDD.md 與 ART_BIBLE.md 引導開發者確認：

- 玩家攻擊特效。
- 特殊技能特效。
- 敵人攻擊特效。
- 命中特效。
- 爆炸特效。
- 道具取得特效。
- Boss 攻擊提示。
- 玩家受傷回饋。
- 技能色彩與視覺風格。

已經確認的技能功能及美術色彩不得重複詢問。

### 工具選擇

如果 game-skills.txt 中包含 PixelFX，且已驗證可用，應優先檢查它是否適合生成目前需要的特效。

閱讀實際 PixelFX Skill 的使用說明與參數規格。

依照工具真正支援的功能執行。

若指定工具不可用，提出：

- ImageGen 生成特效素材。
- Phaser 粒子系統。
- Phaser Tween 動畫。
- 程式生成幾何特效。
- 其他已安裝且適合的 Skills。

替代方案必須符合已確認的美術規範。

### 建立 JSON

建立 config/vfx-generation.json。

每個特效項目依需求包含：

- id：特效名稱。
- category：特效分類。
- description：視覺描述。
- generator：使用工具。
- prompt：生成提示詞或描述。
- colors：色彩規格。
- frameWidth：單格寬度。
- frameHeight：單格高度。
- frames：畫格數量。
- fps：播放速度。
- loop：是否循環。
- duration：特效持續時間及單位。
- transparent：透明背景要求。
- anchor：特效對齊位置。
- trigger：遊戲內觸發時機。
- blendMode：混合模式。
- output：輸出路徑。
- status：生成狀態。

若特效採用程式生成，應使用適合程式實作的設定，而不是強制要求 spritesheet。

特效生成 JSON 必須區分專案自訂欄位與工具實際支援的參數。

### 完成條件

- 必要戰鬥或互動特效已規劃。
- 與美術風格一致。
- 特效生成方式已確認。
- JSON 格式有效。

## STEP 10：生成及處理遊戲素材

建議時間：70–90 分鐘。

### 目標

根據已確認的規格生成正式遊戲素材。

### 前置條件

讀取：

- GDD.md。
- ART_BIBLE.md。
- IMAGE_GENERATION.md。
- VFX_DESIGN.md。
- SKILLS_REGISTRY.md。
- config/image-generation.json。
- config/vfx-generation.json。
- references/。

### 素材生成順序

按照優先順序：

1. 玩家角色或主要互動物件。
2. 核心玩法必要素材。
3. 一般敵人或其他主要遊戲物件。
4. 場景背景。
5. 技能及互動特效。
6. 特殊敵人及 Boss。
7. 道具及 UI。
8. 其他裝飾素材。

實際順序依 GDD 與素材優先順序決定。

### 圖片生成原則

每次生成素材時必須參考已確認的美術規範、概念圖及角色標準設定圖。

不得在每次生成圖片時自行更換風格。

同一角色的不同動作及狀態應維持：

- 角色造型。
- 色彩。
- 身體比例。
- 視角。
- 光影方向。
- 細節程度。
- 素材尺寸規格。

### 素材處理

AI 必須依照實際素材需求，自動進行必要的圖片處理。

包含：

- 圖片裁切。
- 背景移除。
- 透明度處理。
- 多物件圖片分離。
- 尺寸調整。
- 格式轉換。
- 動畫畫格切割。
- Spritesheet 整理。
- 素材朝向修正。
- 邊緣及多餘留白處理。
- 背景循環及捲動處理。

背景處理方式依遊戲類型及實際設計決定。

應優先使用已安裝且適合的 Skills 或其他已驗證工具。

若有必要，可選擇合適的圖片處理函式庫。

不得將 Sharp 或其他特定圖片處理工具強制設定為唯一方案。

不得要求開發者手動使用 Photoshop、ComfyUI 或其他額外工具完成必要素材處理。

### 素材資料夾

依照實際需求建立：

    art/raw/
    references/
    public/assets/sprites/
    public/assets/enemies/
    public/assets/bosses/
    public/assets/backgrounds/
    public/assets/items/
    public/assets/vfx/
    public/assets/ui/

原始生成圖片應保留於 art/raw/。

處理後可供遊戲使用的正式素材放入 public/assets/ 對應位置。

不得直接破壞或覆蓋原始生成圖片。

### 特效生成

依照 config/vfx-generation.json 執行。

優先使用已確認且適合的 PixelFX Skill。

依照實際工具輸出格式處理特效。

若採用 Phaser 粒子系統、Tween 或程式生成特效，應記錄其實作方式，而非捏造不存在的圖片檔案。

### 建立素材清單

建立 config/asset-manifest.json。

每筆素材依實際需求包含：

- id。
- 素材分類。
- 實際檔案路徑。
- 原始圖片尺寸。
- 遊戲顯示尺寸。
- 動畫畫格尺寸。
- 動畫畫格數量。
- 載入方式。
- 使用場景。
- 素材狀態。

所有已完成的檔案路徑必須實際存在。

### 素材品質檢查

檢查：

- 圖片是否符合美術風格。
- 素材尺寸是否正確。
- 素材朝向是否正確。
- 透明背景是否符合需求。
- 是否存在不必要的文字、水印或裝飾。
- 動畫畫格是否完整。
- Spritesheet 是否能正確播放。
- 素材是否能在遊戲中正確載入。
- 背景是否能正常呈現或捲動。

### 完成條件

- 核心玩法必要素材已生成。
- 素材已完成必要處理。
- 已執行素材品質檢查。
- asset-manifest.json 已建立。
- 未完成素材已記錄。
- 正式素材可供遊戲程式使用。

## STEP 11：建立遊戲數值與平衡設定

建議時間：90–100 分鐘。

### 目標

將遊戲數值集中管理，方便後續測試及調整。

### 建立文件

建立 GAME_BALANCE.md。

根據 GDD.md 及核心玩法原型，規劃合理的初始數值。

### 數值規劃

以下為戰鬥型遊戲的範例，依實際遊戲類型調整。

#### 玩家數值

- 最大生命值。
- 移動速度。
- 基礎攻擊傷害。
- 攻擊間隔。
- 子彈速度。
- 受傷無敵時間。

#### 技能數值

- 技能傷害。
- 技能範圍。
- 冷卻時間。
- 持續時間。
- 使用消耗。

#### 敵人數值

- 生命值。
- 移動速度。
- 攻擊傷害。
- 攻擊頻率。
- 生成頻率。
- 擊敗分數。

#### Boss 數值

- 最大生命值。
- 攻擊模式。
- 攻擊間隔。
- 階段轉換條件。
- 戰鬥時間。

#### 道具數值

- 回復量。
- 強化倍率。
- 持續時間。
- 掉落機率。

#### 關卡數值

- 關卡時間。
- 敵人波次。
- 難度曲線。
- Boss 出現條件。
- 勝利條件。

### 訪談原則

向開發者解釋不同數值會如何影響遊戲體驗。

例如：

- 偏向簡單、容易上手。
- 偏向平衡、具有挑戰。
- 偏向高難度及技巧要求。

由 AI 提出合理初始數值，不要求開發者逐一決定所有技術數字。

重要遊戲體驗方向必須經開發者確認。

### 建立 JSON

建立 config/game-balance.json。

依實際遊戲類型建立對應欄位。

必要數值必須具備明確單位。

例如：

- 移動速度：pixels/second。
- 時間：milliseconds 或 seconds。
- 傷害：生命值扣除量。
- 機率：0 至 1。

同一類型的數值應維持一致單位。

不得混用不同時間單位而未明確標示。

### 程式整合

遊戲程式應讀取正式數值設定。

替換核心玩法原型中的暫用數值。

避免將需要調整的遊戲平衡數字分散硬編碼於不同程式檔案。

### 完成條件

- GAME_BALANCE.md 已建立。
- game-balance.json 已建立。
- 數值單位明確。
- 數值符合已確認玩法。
- 程式可正確讀取設定。
- 初始遊戲體驗方向已確認。

## STEP 13：遊玩測試、修正及最終交付

- 數值是否符合預期。
- 玩家是否可以完成關卡。

- 素材風格是否一致。
- 角色及遊戲物件是否容易辨識。
- 背景是否影響遊戲操作。
- 技能及特效是否具有清楚回饋。
- UI 是否容易閱讀。

#### 效能及穩定性

- 是否出現明顯卡頓。
- 遊戲物件是否持續累積。
- 是否存在瀏覽器錯誤。
- 是否可以正常重新開始遊戲。

### 開發者遊玩

- 操作是否直覺？
- 核心玩法是否有趣？
- 遊戲難度是否合理？
- 視覺是否符合預期？
- 哪些地方最需要改善？

1. 無法啟動。

3. 無法操作。

5. 無法完成關卡。
6. 勝敗條件錯誤。
7. 素材載入錯誤。
8. 明顯影響遊戲體驗的問題。

## 10. 時間管理與 Demo 範圍

本課程目標為 120 分鐘。

各階段時間為建議預算，不保證工具安裝、圖片生成及環境問題一定能在預算內完成。

### 10.1 時間配置

| 階段 | 工作內容 | 建議時間 |
|---|---|---|
| STEP 00 | 遊戲類型確認 | 00–02 分鐘 |
| STEP 01 | Skills 安裝與驗證 | 02–05 分鐘 |
| STEP 02 | AI 開發規範 | 05–10 分鐘 |
| STEP 03 | 專案工作流程 | 10–15 分鐘 |
| STEP 04 | 遊戲企劃 GDD | 15–25 分鐘 |
| STEP 05 | 核心玩法原型 | 25–40 分鐘 |
| STEP 06 | 美術規範 | 40–50 分鐘 |
| STEP 07 | 概念藝術 | 50–60 分鐘 |
| STEP 08 | 圖片生成設定 | 60–65 分鐘 |
| STEP 09 | 特效生成設定 | 65–70 分鐘 |

| STEP 12 | 遊戲整合 | 100–110 分鐘 |
| STEP 13 | 測試與交付 | 110–120 分鐘 |

### 10.2 功能優先順序

依照 GDD 及 WORKFLOW 將功能分為 P0、P1、P2。

#### P0：必要功能

缺少此功能將無法完成核心遊戲體驗。

縱向射擊遊戲範例：

- 玩家移動。
- 玩家射擊。
- 敵人生成。
- 碰撞及傷害。
- 生命值。
- 勝敗條件。
- 重新開始。

#### P1：重要功能

能明顯提升遊戲體驗，但不是核心玩法運作的必要條件。

例如：

- 特殊技能。
- Boss。
- 道具。
- 武器升級。
- 正式角色動畫。
- 戰鬥特效。
- 美術及 UI 改善。

#### P2：延伸功能

時間充足時才實作。

例如：

- 多個關卡。
- 額外角色。
- 複雜劇情。
- 多種遊戲模式。
- 大量額外動畫。
- 成就系統。
- 排行榜。

上述分類僅為範例。

實際優先順序必須依遊戲類型及已確認的 GDD 決定。

若 Boss 是核心玩法的一部分，則應列為 P0，而非固定列為 P1。

### 10.3 時間不足處理

當預計無法於剩餘時間內完成所有功能時：

1. 檢查目前剩餘時間。
2. 確認未完成的 P0 功能。
3. 優先完成核心玩法。
4. 提出縮減 P1 或 P2 功能的建議。
5. 向開發者說明影響。
6. 更新 GDD.md 與 WORKFLOW.md。
7. 更新 PROGRESS.json。
8. 保留必要測試及交付時間。

不得為了完成更多功能而犧牲遊戲可玩性。

不得省略必要設計文件及實際驗收。

## 12. 正式專案開發規範

本章包含教師已指定的正式規範，以及開發過程中經開發者確認後追加的專案決策。

不得擅自修改教師指定的固定規範。

### 12.1 固定開發技術

- 遊戲框架：Phaser。
- 程式語言：JavaScript。
- 網頁技術：HTML、CSS。
- 開發工具：Vite。
- 執行平台：桌面瀏覽器。
- 操作方式：依已確認的 GDD。
- 物理及碰撞：優先使用 Phaser Arcade Physics，必要時依玩法調整。

### 12.2 開發方法

- 使用 Codex 作為主要 AI 開發工具。
- 採用規格驅動開發。
- 先確認核心玩法，再進行正式美術製作。
- 依遊戲類型建立適合的設計規格。
- 由 AI 建立及維護規格文件。
- 所有正式設計以開發者確認的內容為準。
- 設計規格與程式實作必須保持一致。

### 12.3 Skills 規範

- 必要 Skills 以 game-skills.txt 為準。
- 必須依實際安裝說明完成安裝。
- 使用前必須閱讀 SKILL.md。
- 必須驗證實際可用能力。
- 不得捏造工具指令。
- 不得擅自增加會產生費用的工具。

### 12.4 圖片生成規範

- 優先使用已驗證可用的 ImageGen 或其他已確認圖片生成能力。
- 先建立 Art Bible。
- 先生成概念藝術及必要標準設定圖。
- 概念藝術經確認後才開始正式素材生成。
- 正式素材必須參考已確認的視覺規格。
- 使用 JSON 管理圖片生成工作。
- 原始生成素材必須保留。
- 由 AI 處理必要圖片加工。
- 不強制使用特定圖片處理函式庫。

### 12.5 技能與特效規範

- PixelFX 已安裝、已驗證且適用時優先使用。
- 依實際工具支援的功能生成特效。
- 可搭配 Phaser 粒子系統。
- 可搭配 Phaser Tween。
- 可搭配程式生成特效。
- 由規格文件及 JSON 管理特效。
- 特效必須經過實際輸出或遊戲內驗證。

### 12.6 測試規範

- 必須實際啟動遊戲。
- 必須檢查必要素材。
- 必須驗證核心玩法。
- 必須提供開發者實際遊玩方式。
- 必須記錄真實測試結果。
- 不使用 Playwright 作為必要測試工具。
- 無法直接執行的測試應明確記錄並請開發者協助。

### 12.7 禁止事項

- 不使用 Godot。
- 不使用 Unity。
- 不使用 Git 作為必要教學流程。
- 不使用 Playwright 作為必要測試流程。
- 不要求開發者手動生成或加工必要美術素材。
- 不使用未經授權的付費 API。
- 不購買未經授權的付費素材。
- 不直接跳過設計訪談。
- 不擅自決定重要遊戲創意。
- 不捏造不存在的工具能力。
- 不將未驗證的成果標記為完成。

### 12.8 專案啟動紀錄

此區域由 AI 在 STEP 00 完成後建立及更新。

記錄：

- 已確認的遊戲類型。
- 已確認的初步 Demo 範圍。
- 開發者的重要初始決策。

此處的啟動紀錄僅作歷史紀錄。

此區域由 AI 在 STEP 02 及後續必要階段追加經開發者確認的專案規範。
